## U1 [P1] 首帧超时被应用于整个健康运行，约 20 秒就停止

位置：src/client.js:470–471、506–513。

deadline 在 runStream 开始时设置为当前时间 + 20 秒，
watchdog 之后始终检查 now()>deadline，没有以 firstFrame 是否已到达为条件。
因此首帧早已收到、最新画面仍连续到达的正常预览，也会被判 intake-timeout 并关闭 Host。

证据：browser-repro-current-result.json 的 healthyStreamPastFirstFrameDeadline。
在连续出帧时把客户端时钟推进 30 秒，绘制帧仍由 1 增至 24，
却变成 error/intake-timeout、running=false，并发送了 Host stop。
这是在正常首帧后验证的健康数据流；不是停帧模拟。
不必实际等待 20 秒，也没有创建真实 WE 窗口。

要求：首帧等待的期限只约束尚未得到首帧的阶段；
首帧到达后继续使用独立的无帧期限与真正的本轮预览时限，
不能把正常播放到 20 秒当作故障，也不能为放行健康流取消停帧监测。

回归：
1. 连续真实/模拟帧持续超过首帧期限，仍 playing、不请求 stop。
2. 首帧未到和后续停帧仍按各自期限结束并清理。
3. 明确的 Host 预览时限到达/EOF 仍正常撤图。
4. 20 秒以上持续运行必须在下一轮实机验收包含，防止短测漏掉。

## U2 [P2] 停止清理中的 reattach 又建立了永久报告定时器和重复监听

位置：src/wallpaper/session.js:132–140、285–296、171–175。

runClose 先清掉 reportTimer，随即调用 reattach。
活着的 child 会再增加 stdout 与 close 监听，并重新创建每秒写 preview-status.json 的定时器。
之后源窗口关闭成功，child close 的回调调用 stop，但 stop 因 closed=true 直接返回，
没有清掉新定时器。退役的 session 仍被定时器持有，持续进行日志写入；
每轮停止都会再留下这样的工作。

证据：host-repro-with-timer.json 的 reportTimerAfterStop。
使用真实 createPreviewSession、假 helper/child，确认已关闭后也模拟了 child close：
before=1、after=1、sourceClosed=true；close 监听由原本 1 个变成 2 个。
正常停止之后，应当为 0 个报告定时器。

要求：清理和重试不能重新启用采集报告循环或重复订阅。
保留同一窗口身份、在途清理幂等和失败后的真正关闭重试，
让成功停止、自然结束、失败清理与卸载都取消该轮定时器与监听。
不要用 unref 代替取消，它只是不阻止进程退出，日常 Host 活着时仍会执行。

回归：跟踪真实会话创建的定时器/监听，
正常停止、失败后重试成功、自然结束与卸载后计数应归零/恢复基线，
后续运行不应积累前几轮的日志写入。
为这项测试可使用假子进程和自有输出目录，不需要真实窗口。
