## R2 / P2：启动参数不等于实测尺寸；关闭发送不等于关闭验证

报告122行示例 `--we-open ... 1302 776` 没带 `--initial-offscreen`。当前 `Program.cs:28–47` 和 `SourceWindowHelper.cs:304–321` 表明：只有有initialPosition时才追加 `-x/-y/-borderless`；因此此示例默认有边框，不能直接复现本轮initial-position来源的窗口条件。1302×776是本轮实际物理客户区/capture尺寸，不是已证明等价的启动参数值；CLI尺寸、DPI和实际客户区要分别记录。官方也把width/height与borderless列为独立选项：[WE命令文档](https://help.wallpaperengine.io/en/functionality/cli.html)。

请给出一个明确可执行分支，不再写“helper或CLI”后省略差别：

- 指定已有可信helper及校验依据、实际argv与新鲜唯一location；若使用原屏外启动路径，再用经过身份检查的NOSIZE坐标移动恢复可见，保持本轮前史；若直接屏内启动，明确这是另一条件，记录为限制。不要凭1302数字保证实际视口等价。
- 打开返回的wePid是launcher PID（Program.cs已明确note），不能当实际渲染PID；等待唯一location窗口，验证HWND、原WE可执行路径/启动时间、非最小化/cloaked，再记录物理外框/客户区/style/exStyle/工作区DPI。无捕获组不用假造capture尺寸或新帧证明；初始化完成由用户实际观察确认，没看到有效动态就不能算平滑。
- 只允许短暂helper操作进程，不启动capture模式/Host会话；“完全不启动WallpaperProbe”与用该exe作控制命令矛盾，应写清两种模式。不能通过运行helper的成功退出码证明源已渲染或没有别的采集器。

## R3 / P2：把生命周期和资源竞争推测写回源码能证明的范围

**生命周期主要判断可以保留，机制保证需要纠正。** 报告86–88行说任意原因退出都会在finally关闭、强杀也直接触发关闭，不符源码：

- `Program.cs:345–359` 需要 `ownedLocation != null && parentLost`；parentLost仅列parent-stop/pipe-disconnected/pipe-eof/stdin-eof，并且还需CanCloseOwned允许。worker未结清时明确拒绝关闭；强制终止不保证执行finally。
- `session.js:550–558` 子进程close会stop，但 `runClose:320–373` 先等待子进程及worker终态，forceKilled、非零退出或未知worker会返回worker-unconfirmed保留窗口，不是“立即证明并强制关闭”。

准确结论应为：**现有受支持的日常停止路径会进入拥有源的清理流程，没有公开的WGC暂停/停采留源接口。不能靠强杀制造可接受控制组。** 这不需要证明所有异常路径都必然关闭，亦不能把异常残留源当合法对照。

报告57行称D3D11表面被持续“排他性锁存”，没有现有证据。`StagingReadback.cs:38–58` 实际创建staging纹理，从捕获surface取得texture后CopyResource到staging，再Map(staging, Read)并Unmap；不能据此认定一直排他锁住WE源渲染表面。可以保留“拷贝/同步等待和CPU编码负载可能间接影响源、尚无本轮因果测量”。微软说明捕获帧提供Surface并需及时释放；这也不是源渲染被持续独占锁定的证明：[WGC帧处理](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)。
