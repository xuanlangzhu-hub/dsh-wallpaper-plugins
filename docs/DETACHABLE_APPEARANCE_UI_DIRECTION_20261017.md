# 独立外观窗口：壁纸库与详情设置的UI方向

2026-10-17。用户提出：独立窗口不应原样搬入现有通用设置长表单；希望像Wallpaper Engine一样看到壁纸预览图、点击选择，并在每张壁纸下看到对应壁纸自己的设置。

这是后续UI/产品方向记录。最新接续：P0七审补修及宿主升级已完成，日常为DSH0.2.1-rc.2/外观rc.35。[P1A正式接入任务](GEMINI_NEXT_DETACHABLE_APPEARANCE_P1A_20261017.md)先接窗口生产链路，之后P1B按本文整理库/详情与共享控件，作者参数另拆；不安装或操作日常应用。下文布局仍是待实现方向，不称当前UI已交付。

## 建议的首版布局（待细化，不称已实现）

- **壁纸库**：图像卡片显示预览图、名称和选中/正在播放状态；点击卡片查看该壁纸，应用/开始动作明确。没有预览图有占位，不依赖悬停或启动每张壁纸生成动态预览。
- **当前壁纸详情**：显示较大预览、标题及播放状态，下面集中放该壁纸的参数和保存/重置等动作。先推荐只展开当前选中壁纸的设置，不把全库每张卡片都展开成长表单。
- **DSH外观**：文字可读性、聊天底色、主题/强调色等单独分组或页签，避免与壁纸作者提供的参数混淆；当前四字段壁纸外观预设继续保留明确保存/应用语义。
- **独立窗口**：宽时用“卡片区＋详情区”，便于浏览和调参；窗口窄时能切换库/详情。
- **侧边吸附**：紧凑壁纸入口＋当前壁纸详情纵向展开，保持主会话/背景可见；两种形态复用业务控件和确认状态，不要求像素布局完全相同。

“每张壁纸有自己的设置”分两层：已有的DSH亮度/遮罩/模糊/界面不透明度，和壁纸作者公开的专属参数。用户所说的后者是明确需求，但不能拿现有四项冒充已完成。主题色等是否以后跟壁纸保存仍另定，不顺带扩大当前预设范围。

## 已有接缝与实际缺口

源码`src/wallpaper/catalog.js`已识别受限项目中的预览文件，并在`publicCatalogItem`输出`previewRef`（wallpaperId/kind），可作为后续缩略图服务输入；这不等于当前UI已经能直接显示预览，也不能把本地绝对路径直接交给浏览器。

作者参数的schema提取、控件映射、向本轮独立源应用以及保存/恢复仍需独立调查/验证。先支持已确认的开关、滑块、颜色和枚举；未知属性标未支持，不承诺全部壁纸完整复刻。需核对修改只作用于DSH这一份源，不能意外改动用户桌面WE实例或全局配置；没有验证前不提供假生效控件。

## 推进顺序

1. 先闭合P0剩余通信、连接时序和资源归属问题。
2. 进入完整UI编码前，先给出一个简洁的库/详情布局草案，明确独立与吸附两种尺寸下的结构；不照搬设置长表单。此处没有要求立即开浏览器、截图或做多套原型。
3. 首个可用版本整合预览图选择、现有可用调节项和窗口切换；缩略图服务和选择/播放状态需有实际证据。
4. 作者专属参数另拆受限接入任务，验证最小单项的目标隔离与真实生效后再扩类型，不用这一整套参数能力拖住窗口基础交付。

上述布局和分期是Codex建议，最终细节待后续确认；用户已明确的是“重整UI、可视化选壁纸、按壁纸显示自己的设置”。本轮只记录，不开新P1编码、不打包安装、不跨会话消息。
