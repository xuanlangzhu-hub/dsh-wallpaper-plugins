## 实机各阶段

真实操作前由用户确认方便、暂停其它助手。候选安装和恢复仍由 Codex 备份/核验，界面由用户点击。
**先临时装入同一 rc.23，再测 A0 到 A1**：不能 A0 用 rc.1、D 用 rc.23，把版本差异归给壁纸。
DSH 始终打开在同一静止会话、同一前台位置，后台助手/模型生成暂停；测试时不要滚动、改大小、
点实验任务栏入口或改变前台。输入/滚动测试已有验收，本轮不和资源静态测量混在一起。

| 阶段 | 存在的本轮资源 | 不存在的本轮资源 | 主要回答 |
| --- | --- | --- | --- |
| A0 | 原桌面 WE；DSH rc.23 普通主题 | 额外源、采集、壁纸画面流 | 相同宿主版本的开始基线 |
| B | A0 + 一张屏幕外无边框 Lucy 源 | 原生持续采集、Host 画面流、客户端壁纸播放 | 增加该场景源的成本 |
| C | B + 原生 `memory` 模式采集/JPEG/哈希 | pipe 传输、Node 画面流、客户端播放 | 原生处理链的成本 |
| D | 原桌面 + 正式 rc.23 壁纸链路，日常模式 | B/C 的额外源与旧采集 | 实际插件完整播放成本 |
| A1 | 同 A0，停止本轮链路 | 本轮源、采集、播放 | 清理和基线漂移检查 |

B→C 可复用同一窗口；C→D 先确认 C 的采集已结束、唯一源已关闭，再由用户点击正式开始。
D 由现有 Host 创建新源，不能同时留着 B/C 的源。记录不同 location/HWND、相同场景和实际尺寸。
先停止 D、验证 A1，再让用户退出，恢复本轮备份与日常 rc.1；用户重开确认日常正常后结束。

每阶段正常稳定后暖机约 **10–15 秒**，资源采样预算 **45 秒**，`IntervalMs=1000`、
`RediscoverEvery=12`，顺序 A0→B→C→D→A1。Get-Counter 和发现过程会使实际耗时超过预算，
只把有效目标存活期间的记录纳入。C 的原生采集应预留足够时间（例如有上限的 180 秒），
不能在采样完成前到期；需要提前结束时用本轮 `stop.txt`，验证退出后只关本轮窗口。
各阶段不能并行测，以免采样器/额外源叠加。首轮不自动重复；不足或条件改变时只解释/补受影响阶段。

## 质量和运行条件

- Lucy 白名单项目及文件指纹一致，已有属性/WE 全局设置保持原样；不猜 `-fps`、不全局 pause/stop/mute。
- 使用 rc.23 相同无边框、初始屏幕外路径。请求尺寸 1280×720；Inspector 的窗口坐标/宽高不自动等于
  物理帧尺寸。历史 1302×776 只是旧轮次实测，不硬编码成当前必然尺寸。C/D 取原生帧实测宽高核对。
- B 不为“测 FPS”偷偷增加采集；B 的 frameSize、变化帧和真实 sourceRenderFps 不可得时明确 unknown。
  核对 B 的窗口身份、可见但屏幕外、非 Iconic/非 Cloaked。B 的来源条件只能作为受控近似，不能声称逐帧同工作量。
- `scenes.js` 的 FPS=30 是**采集循环上限**，不是 WE 源限帧。C/D 记录实际处理/变化帧率；D 再记录接收、
  绘制、丢弃和解码错误。计数取测量边界内的增量/真实秒数，不拿含暖机的累计计数当该阶段 FPS。
- sourceRenderFps 未测得就一直 null。场景相位、后台策略、背压可能改变实际工作量；不能凭相同请求尺寸
  就声称同画质同 FPS。若 C/D 帧尺寸变化，该项对照不可用；若实际吞吐不同，资源差异只作描述。
- 记录 DSH 窗口尺寸/DPI、前台应用、交流电/电池、系统/WE 电源策略、原桌面播放状态；不改系统设置。
A0/A1 都在 DSH 前台测得，不能泛化成“桌面可见时”或“游戏时”的负载。

## 怎样认进程

使用 [清单模板](perf-phase-manifest.example.json)。模板 state=template，空身份均是待填，不能当实测清单。
实际证据放新建的 `.tmp/source-cost-<日期时间>/`；manifest、原始 sample、窗口/Host 边界快照、
清理结果分别保存。不要引用旧 PID 或清空历史目录。

| 角色 | 取证依据 | 特别注意 |
| --- | --- | --- |
| `we` | 原 WE 的 PID/StartTime/可读路径；唯一源窗口的 owner PID | `--we-open` 返回 wePid 是短命 launcher，不是渲染进程。窗口通常属于原 WE；两个角色共享 PID 时只采一次 |
| `capture` | 自己启动的 child PID + StartTime + helper 指纹；D 可取 session.childPid | 不把短命窗口查询/helper launcher 当持续采集 |
| `dsh-app` | 当前官方 EXE 路径、主窗口 owner PID 与启动身份 | 不按进程名匹配所有同名实例 |
| `dsh-host` | 该实例实际 Host 所在进程的父子关系/可读路径等证据 | Host 可能共享主进程，不能假定一定有 node.exe |
| `dsh-client` | 当前 DSH 页所在 renderer 的实例/进程关系 | 不能靠“CPU 最高”猜 renderer；无法唯一识别时 unknown，不能算客户端增量 |
| `dsh-gpu` | 当前官方实例的 GPU 子进程及关联证据（取得才写） | 与 renderer/其它视图可能共享；不把它称为仅壁纸 GPU 成本 |

角色可由同一进程承担：`processes` 每个 PID+StartTime 只出现一次，`roles` 可以多个；按 PID 去重后交采样器。
同一角色也可对应多个有证据的进程，逐 PID 展示。不能抓所有 node.exe、所有 renderer，或把父子 CPU 当重复“总量”。
各阶段开始/结束复核 identities；新进程由清单显式加入，采样器不会自动跟随。身份不能确认就标未知，
不能为了跑满表格默认猜一个 PID。采样器自身的 pwsh 成本也记录为观察干扰，不能当插件子进程。

D 可取现有 `preview-status.json` 的 childPid、window.pid/location、native、client，以及 hub 统计；
在测量开始/结束各复制一份到新文件，避免下秒重写。客户端角色 PID 不由这些统计直接提供，必须另证。
C 保留原生 frames.jsonl/status/summary。帧日志只有最近 1200 条，可能不覆盖整个测量窗口；标实际覆盖范围，
不要把结束 summary（含暖机/尾段）直接作为阶段计数。B 不采集，变化帧字段为空是正常的。

## 对比规则

离线脚本先出每阶段、每 PID、每 LUID 的数值与覆盖，再出允许的差值；规则见 DS 小任务。
首轮最低可比门槛：同一逻辑容量；身份与阶段相符；CPU 至少 **5 个有效区间/30 秒累计有效时间**；
内存/GPU 至少 **5 个有效观察值**，并列出总记录数、有效数与阶段测量时长。
这是初筛门槛，不是统计置信度或稳定性证明。零分母和缺失值都不能补成 0。

CPU 按有效原始 delta/time 重算。工作集/私有字节分别取有效观察均值，说明不等于进程独占物理内存。
四项 GPU 内存按 PID+LUID 分别展示均值/有效数；不相加成单一“真实显存”。
GPU 按 PID+LUID+engineType 展示**每次实例最大值的观察均值、阶段最大值与有效数**；
这是 per-process engine 指标，不是整张 GPU 比例。实例集合变化要提示；拓扑有 unknown/变化时 GPU 只分段展示，
不拼成整阶段可比均值。CPU 覆盖仍可独立评价，不能因 GPU 缺失把 CPU 一并造零。

| 对照 | 可表达的结论 | 不得表达 |
| --- | --- | --- |
| B 与 A0/A1 | 同一个 WE 进程增加源时的观察变化；基线前后范围同时展示 | 新 source PID 的独占成本；游戏性能损失 |
| C 与 B | 新采集 helper 成本、共享 WE 的变化 | 原生采集/JPEG 之外也自动分离每个步骤 |
| D 与 C | 完整链路与离线原生链的差异、D 中各角色读数 | 纯 renderer/纯解码成本（还包含 pipe、Host、调度/背压差异） |
| D 与 A0/A1 | 当前窗口/场景/前台条件下完整运行的观察增量 | 全 GPU 百分比、帧同步实验、通用低开销或数日稳定 |
| A1 与 A0 | 清理后各指标和身份的恢复/漂移 | 一次工作集未回落就确认内存泄漏 |

以 A0/A1 分别计算参考差值，不把两个不同时段的基线先平均再装成精确值；不截掉负差值。
基线明显漂移或前台/电源条件变化时给 inconclusive，保留原数值；首轮不自动叠加更多测试。
最终哪项值得优化由 Codex 根据分层成本、有效覆盖、吞吐/清晰度与用户观感决定，不由脚本自动下结论。
