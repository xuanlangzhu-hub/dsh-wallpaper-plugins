## 1. 逐项结论

编号沿用Gemini原报告，不另造一批重复问题。

| 编号 | 独立判断 | 应如何处理 |
| --- | --- | --- |
| G1 停止与尾批竞争 | **机制成立，属于已知接缝，概率表述未证实。** 受控真实client/路由重放：普通批次204、停止落快照、尾批409；文件只含seq1/2，seq3未到，finalized=false、degraded。此前四/五审已经记录409后应如实降级，六审L1-A正例只保证摄取窗口仍开放时能补发，未证明生产关闭时序保证收齐。 | 建议P2诊断可用性问题，不能直接称高危播放故障或“极大概率”。后续补真实关闭/导出时序的有界收尾策略，失败继续明确不完整；禁止为诊断无限等待或改变播放生命周期。 |
| G2 自然结束/失败不送尾批 | **自然EOF成立，失败部分不成立。** 真实connect/runStream遇EOF后，2条尾部记录留在内存，0次trace POST、0次stop命令；受控stream-error则会进入`if (failed) await stop(...)`，实际送出isStop=true、2条记录并调用stop一次。 | 只补自然结束的统一诊断收尾，建议P2；与G1一起验证真实关闭窗口。原文“失败也完全不触发”应删除；“不足64条”也与当前150分片、500ms周期冲刷不符。 |

| G5 32流静默淘汰 | **成立，与六审L1-B-cap完全重叠。** 六审已有真实路由、32→33、未发3/早期0、单连接多代次及健康正例。 | 合并为同一个P2任务，不重复计数或重写。按六审保留有界摘要/未知标记，不能提高上限代替正确处理。 |
| G6 同activeRun跨generation导致健康翻倍 | **求和风险有条件成立，但文中运行触发链未成立。** 沿用G3不存在的重连路径；真实客户端重新start后会换activeRun，独立控制中旧轮overflow=1、新轮generation改变后overflow=0，并未继承。 | 暂不作为已确认运行缺陷。若要补报，必须证明同一累计计数如何在真实客户端送入多个流，或明确这是协议允许输入的身份/计数语义问题。不能为了假定路径去改P2/P4。 |
| G7 Host事件标量覆盖 | **核心成立，新增且值得修。** 同seq的A latest-overwritten跳5帧，B duplicate-sequence，结果latest=0/skipped=0而应1/5；两次背压写入只记1。hostStreamWrites也确实缺sequence。 | 建议P2：Host逐连接事件也应保留并正确统计。背压若有意按“帧”计数，应明确名称/口径；不能把事件数与帧数混称。缺sequence是实现缺口，但正常单连接时单调时间排序通常等价，不能仅凭NaN断言日常排序已经出错。 |
| G8 native/Host校验与时钟过滤 | **成立，已复现。** native写入时刻10、-5，schema违规0、间隔mean=-15，状态仍available；Host错域事件虽然使state=degraded，却仍进入统计，污染出1000ms间隔。 | 建议P2：统一必要字段/时钟域校验，错误记录不得进入数值统计，不能仅打degraded标签后继续混算。原文“污染computeIntervals”有效，但并非所有NaN都会留下NaN输出，computeStats会过滤非有限数。 |
| G9 未检查native flushFailed | **字段遗漏成立，已复现输入flushFailed=true而分析available。** 但C#在实际写盘前序列化该字段：某次成功重试的JSON可能仍携带前次失败值，不能笼统解释为本次文件一定不完整。 | 建议与G8合并P2健康语义补修：先明确标志表示本次、前次还是历史失败，再让导出和分析一致。不能为了通过反例而另造不真实的原生成功/失败口径。 |
| G10 原生迟到I/O/误删新导出/CTS | **部分事实成立，核心误删推演未成立。** I/O不接受取消是已知限制；`_activePublishTask`门禁保持到旧任务TryDelete结束后的finally，新Flush在此之前会直接返回false，不能据原文时序让旧清理越过新发布。CTS未Dispose属低优先级资源卫生。 | 不重开已闭合F4或要求操作系统I/O即时取消。误删新文件若要成立需给出越过门禁的独立反例；CTS可作为P3小修，不能借此重构原生发布。 |
| G11 Host重入timer/客户端降级 | **timer事实成立，影响较小；降级范围需要区分。** 重入race的200ms计时器未清除，但到期后自然结清，race已接拒绝处理，不是永久timer泄漏。export失败只改hostTrace，client快照不会显示该标记；这不自动意味着client事件内容损坏。 | timer建议P3，保存句柄并在结清后清除即可。若要单独读client也看见导出健康，应明确共享导出状态；完整分析已读host.degraded，不能称所有诊断都误报正常。 |

这里P2/P3指诊断正确性和资源边界的优先级；没有证据将这些问题定性为日常播放卡顿根因、数据破坏或安全事件。
