## 已确认的实现

当前真实命令为 `--forever 30 pipe --owned-location ... --taskbar-hide`，采集配置上限 30 帧/秒；这是采集目标/上限，不是 WE 源渲染 FPS。

路径是：独立 WE 源窗口 → WGC 表面 → `SoftwareBitmap.CreateCopyFromSurfaceAsync` 回读/等待 → 每帧 JPEG 编码 → WHL1 内存画面流 → DSH `createImageBitmap` 解码并绘制。

原生主循环串行等待回读和 JPEG 编码，再发送这一帧；这些阶段变慢会降低送帧速度，前端收到后还需解码、绘制和合成。因此原生桌面流畅不能推出这条额外链路有相同帧率/延迟。

前端已有 latest-only 待绘制帧与丢旧帧机制，不要把「增加前端只保留最新帧」当成尚未实施的新优化；原生的取帧、表面生命周期与回读等待仍可单独评估。也不要将采集计数、源时间戳间隔或客户端累计绘制/总时长直接当作用户可见 FPS。

## 三个待区分方向

1. 回读/编码吞吐受限：若成立，原生日志中的 `readbackMs`/`jpegMs` 会占满或超过帧预算，送帧已经在前端之前降低。
2. 前端解码/绘制/合成受限：若成立，前台接收稳定但绘制/可见呈现落后，或者前端处理时长和延迟上升。后台时主动不绘制产生的 dropped 不能作为证据。
3. 独立源窗口的渲染/调度受限：需隔离取帧/编码开销后再测。当前捕获帧时间戳间隔包含采样和漏取帧，不能凭它确认 WE 本身渲染速度下降；源窗口额外负载、后台调度与 GPU 等待都尚未排除。

## 后续优化顺序，尚未实施

1. 用三体作为复杂、可交互场景，Lucy 作轻量参照；先取短的前台静止/鼠标移动两个时间段，记录阶段耗时、帧间隔和端到端延迟。固定尺寸/外观/电源条件，不重跑先前 GPU 四段与 35 分钟实验，也不改全局 WE FPS/画质。
2. 优先隔离回读里的 GPU 等待、复制和后台调度：在受监督的独立验证中对比取帧本身、回读与正式 JPEG 传输，保持源与窗口条件一致。再决定是否改取帧/释放时点、复用资源、减少串行等待或重复分配；不要先凭猜测提高上限或替换整个链路。
3. 增加可控的采集帧率、画面尺寸/质量选项，说明画质与流畅度关系。需先减少每帧处理成本；将 30 改为 60 本身无法让 85ms 的处理跑到 60fps。
4. 若逐帧 JPEG 仍是显著成本，评估原生硬件视频编码 → 浏览器硬件解码的低延迟通路。它是架构候选，先做隔离原型，验证编码器/浏览器支持、画质/延迟和源清理，再决定是否进入日常包；尚未确认本机收益，也不保证达到原生 FPS。

Windows [Hardware MFTs](https://learn.microsoft.com/en-us/windows/win32/medfound/hardware-mfts) 与浏览器 [WebCodecs](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API) 是接口线索；具体设备/编码格式支持需实测。前端支持可用 [VideoDecoder.isConfigSupported](https://developer.mozilla.org/en-US/docs/Web/API/VideoDecoder/isConfigSupported_static) 初筛，不能把存在该 API 当作硬件加速或收益证明。

性能与鼠标延迟可以作为后续一项专项，范围由用户恢复开发时确定。先保留已工作的 rc.28、任务栏隐藏、主题恢复和清理门禁，优化不能回退这些已验收能力。
