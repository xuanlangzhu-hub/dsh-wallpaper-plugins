## 当前实际能力与缺口

插件已有深浅主题、深色主题四套配色、全局界面不透明度、聊天区/侧栏不透明底色开关，以及壁纸亮度/遮罩/模糊。深色配色同时携带底色、强调色、按钮和引用颜色，尚未独立开放文字对比度、阅读区域底色强度或自定义强调色。

当前`opaqueChat`可覆盖整个聊天列，`surface`影响通用界面层；它们已有帮助，但不能直接等同于“文字对比度”。当亮壁纸穿过阅读区时，只提高文字亮度未必够，需要阅读区域的底色一起提供分离。

建议按用途分组，避免把DSH界面与壁纸的滤镜混在一起：

| 设置组 | 建议内容 | 具体作用 |
| --- | --- | --- |
| 壁纸画面 | 亮度20–120、遮罩、模糊 | 调整背景媒体与主题色覆盖，沿用已确认范围 |
| 界面可读性 | 文字对比度标准/增强；聊天阅读底色强度 | 增强正文、次要说明及普通工具行与背景的区分；使亮/复杂壁纸下仍可阅读 |
| 主题底色 | 保留既有主题/四配色，后续评估独立底色选择 | 控制聊天/侧栏/卡片的整体背景关系，和强调色分开 |
| 强调色 | 跟随主题／自定义颜色，提供恢复跟随主题 | 作用于主按钮、链接、选中态、焦点等非错误语义的交互元素 |

后面三行的控件形式是建议，还未确定最终数量、强度范围、默认值或迁移方案。不要直接按此表批量增加新字段或改变旧用户外观。

## 本机官方组件的实际颜色归属

只读检查安装目录`resources/app.asar`中的官方模块，未修改该文件或执行其中代码。theme/conversation/primitives模块版本均为0.2.0-rc.2；tool/trajectory实现亦在同一安装归档中检查，以下是此版本的源码事实，不是所有未来版本的保证。

| 元素 | 当前实现依据 | 建议归属 |
| --- | --- | --- |
| 正文 | MarkdownText使用`--dsw-alias-label-primary` | 文字对比度，保留正常正文色 |
| 普通工具行与工具图标 | ToolRow使用DisclosureRow；row为label-tertiary，hover为label-secondary，leading继承color | 与工具说明一起增强可读性，不默认全部染成强调色 |
| 主按钮 | primary-fill/primary-hover搭配label-primary-foreground | 强调色及自动选择的清晰前景色，不能只改背景不顾按钮文字 |
| 普通Markdown链接 | 专用`--dsw-alias-link` | 强调色；现有palette没有全面覆盖它，单改brand不等于所有链接都会变 |
| 引用/业务高亮及部分焦点 | state-business-primary/tertiary；focus-ring-color有business-primary回退 | 可纳入强调色，但不把business与success混同 |
| 选中导航/交互背景 | sidebar active-accent、interactive-bg-active等 | 强调色派生的实色/透明底色 |
| 成功、错误、警告/状态点 | StateDot和工具详情使用state-success/error/warn系列；ToolRow的错误摘要/差异增删亦有独立语义色 | 保留语义，避免用一个强调色抹掉状态差异 |
| 文件类型图标 | FileTypeIcon按代码/文件夹/PDF/表格等使用不同静态色，支持组件级override | 首步保持类型识别，不承诺随全局强调色统一变色 |

这说明“强调色能改一些会话元素”确实有现成接缝，但不存在一个可可靠覆盖全部图标/文字的万能色变量。需要先列明确的令牌白名单，再覆盖正常/hover/active/focus及按钮前景色；不用全局`svg { color: ... }`或替换所有蓝/紫色。

## 实现前应保留的边界

- 可读性调节作用于文字/阅读底层；不对整个DSH窗口加CSS contrast滤镜，避免同时改变壁纸、图标与状态颜色。
- 聊天阅读底色应在现有区域底色/透明度能力上设计，兼容旧opaqueChat开关与surface，不堆叠含义相同的多个控件。输入卡片、窗口顶条、菜单、消息裁剪和桌宠已有保护保持。
- 强调色需与主题底色解耦，保留“跟随主题”。目前非默认深色palette用body级`!important`覆盖令牌，新设置必须统一处理投影顺序，不能只写theme tokens而被旧palette覆盖。
- 明亮与深色主题都要保持正文/次要文字/按钮/链接的区分；预设颜色或自动派生hover不等于任意颜色都已验证可读。不要仅凭令牌数值宣称任意动态壁纸都达到固定对比标准。
- 后续将主题设置纳入按壁纸预设时，需版本化扩展并兼容现有四项记录；本次P1仍只保存四滑块，不提前塞入尚未稳定的新主题字段。

## 建议执行顺序

1. 四项外观预设P1已进入编码，先完成它的保存/应用/删除及归属核对，不在同一轮临时混入主题重构。
2. 下一小步优先补“可读性增强 + 阅读区域底色”的明确行为和默认兼容，解决用户提出的亮壁纸文字问题。
3. 再开放独立强调色及其已核对的令牌范围；保留现有主题底色/配色选择，额外自定义底色按实际需要另定。
4. 接入按壁纸预设，之后再做自动随播放切换或独立选择器。120%亮度可随未来功能包一起交付，不为它单独开一轮实验。

这是Codex建议顺序，用户可调整；尚未给主题扩展下编码任务或自动向其它会话发消息。实现时主要仍在插件的主题/设置层，不改官方EXE/app.asar，也不要求修改WE。
